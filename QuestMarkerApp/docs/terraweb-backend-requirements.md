# Τι χρειάζεται η εφαρμογή Quest από το backend του Terraweb2

Το έγγραφο απευθύνεται στην ομάδα του **terraweb2-backend**. Περιγράφει τις αλλαγές που χρειάζονται για να βλέπουν τα γυαλιά Meta Quest 3:

1. τους αισθητήρες στη **σωστή** θέση, και
2. **μοντέλα 3D** (φωτογραμμετρία, BIM, τοπογραφικά) που ανεβαίνουν από τη σελίδα του έργου.

Η εφαρμογή των γυαλιών χρησιμοποιεί ήδη το API του Terraweb2 με τον ίδιο λογαριασμό χρήστη:

| Χρήση | Endpoint |
|---|---|
| Σύνδεση | `POST /api/auth/login/` → `{access, refresh}` (JWT), `POST /api/auth/refresh/` |
| Έργα | `GET /api/project/` |
| Επιλογή έργου | `PATCH /api/auth/profile/ {current_project_id}` |
| Αισθητήρες | `GET /api/sensors/sensors/`, `GET /api/sensors/sensors/{id}/`, `GET /api/sensors/areas/` |
| Μετρήσεις | `GET /api/sensors/measurements/?sensor=…&ordering=-meas_date` |
| Τύποι | `GET /api/sensors/types/{id}/` |
| Συναγερμοί | `GET /api/alerts/events/?active=true` |

Ό,τι ακολουθεί είναι **προσθήκες**. Τα υπάρχοντα endpoints δεν αλλάζουν συμπεριφορά.

---

## Μέρος Α: Συντεταγμένες αισθητήρων (προτεραιότητα 1)

### Το πρόβλημα

Το `GET /api/sensors/sensors/` επιστρέφει τη θέση κάθε αισθητήρα μόνο ως `sensor_geometry` (GeoJSON Point σε WGS84). Στην πράξη αυτό το σημείο έχει συχνά πατηθεί πάνω σε χάρτη. Οι **μετρημένες** τοπογραφικές συντεταγμένες (στήλες x / y / z του αισθητήρα) υπάρχουν στη βάση, αλλά η λίστα δεν τις επιστρέφει. Και το CSV export των αισθητήρων τις βγάζει κενές (X, Y κενά, μόνο Z).

Μετρημένο αποτέλεσμα στο έργο **Κόνιτσα** (40 αισθητήρες): με τις συντεταγμένες ΕΓΣΑ87 του τοπογράφου ως σημείο αναφοράς, οι θέσεις WGS84 του Terraweb απέχουν **κατά μέσο όρο 10 m και έως 45 m** (σημείο T6). Τα υψόμετρα ταιριάζουν ακριβώς. Επομένως τα γυαλιά δείχνουν τους αισθητήρες σε λάθος σημεία και τα μοντέλα 3D δεν ευθυγραμμίζονται.

### Τι χρειαζόμαστε

**Α1. Στο έργο:** το σύστημα συντεταγμένων των μετρήσεων.

```jsonc
// GET /api/project/  (ανά έργο, νέα πεδία)
{
  "id": 12,
  "name": "Κόνιτσα",
  "survey_crs": 2100,            // EPSG του οριζόντιου συστήματος (2100 = ΕΓΣΑ87, αλλά οποιοδήποτε: UTM, άλλα εθνικά). null αν δεν είναι γνωστό
  "survey_vertical": "orthometric", // "orthometric" (από τη θάλασσα) | "ellipsoidal" (GPS) | "local"
  "location": { "lat": 40.0478, "lon": 20.7481 }  // κέντρο έργου σε WGS84 (για αυτόματη αναγνώριση συστήματος μοντέλων)
}
```

**Α2. Σε κάθε αισθητήρα της λίστας** (`/api/sensors/sensors/` και `/api/sensors/sensors/{id}/`): οι μετρημένες συντεταγμένες, και οι ίδιες **μετατρεμμένες σε WGS84 από τον server**.

```jsonc
{
  "id": "0570c4ba-637d-4dd7-ab06-7049b1562c82",
  "name": "A1",
  "sensor_geometry": { "type": "Point", "coordinates": [20.748, 40.047, 447.3] }, // όπως σήμερα
  "survey": {                     // ΝΕΟ: η μετρημένη θέση, null αν δεν υπάρχει
    "x": 222135.527,              // στο survey_crs του έργου
    "y": 4436556.5746,
    "z": 447.314,
    "crs": 2100,
    "lat": 40.0478123,            // ΝΕΟ: x/y μετατρεμμένα σε WGS84 από τον server (PROJ / PostGIS ST_Transform)
    "lon": 20.7481456,
    "measured_at": "2026-03-06T14:23:00Z"
  }
}
```

Γιατί χρειάζονται και `lat` / `lon` υπολογισμένα στον server: τα γυαλιά δεν έχουν τη βιβλιοθήκη PROJ, οπότε δεν μπορούν να μετατρέψουν οποιοδήποτε EPSG του κόσμου. Από WGS84 σε τοπικό σύστημα μπορούν (ο κώδικας υπάρχει ήδη). Με PostGIS:

```sql
ST_Transform(ST_SetSRID(ST_MakePoint(x, y), survey_crs), 4326)
```

**Α3.** Το CSV export των αισθητήρων να συμπληρώνει τα X, Y (σήμερα κενά).

**Κριτήριο αποδοχής:** για την Κόνιτσα, το `survey` των 40 αισθητήρων ταιριάζει με το `EGSA_all_points.csv` του τοπογράφου (διαφορά < 1 cm), και το `lat/lon` επιστρέφει στο ίδιο σημείο με αντίστροφη μετατροπή.

## Μέρος Β: Μοντέλα 3D ανά έργο

### Ροή χρήστη

1. Στη σελίδα του έργου: **«Ανέβασμα μοντέλου 3D»** → zip (OBJ + MTL + εικόνες, πιθανώς πολλά tiles) ή OBJ / DXF / IFC.
2. Ο server προτείνει το σύστημα συντεταγμένων («Φαίνεται ΕΓΣΑ87 (EPSG:2100)») και ο χρήστης επιβεβαιώνει ή διαλέγει άλλο.
3. Η επεξεργασία γίνεται στο παρασκήνιο. Ο χρήστης βλέπει την κατάσταση: *Σε αναμονή → Επεξεργασία → Έτοιμο / Σφάλμα*.
4. Στα γυαλιά: **Μενού › Μοντέλο 3D › Μοντέλα έργου** → λίστα → λήψη → εμφάνιση. Το μοντέλο μένει αποθηκευμένο στη συσκευή για χρήση χωρίς internet στο πεδίο.

### Β0. Δύο φάσεις

Τα μοντέλα είναι **συνήθως ήδη σε μέτρα**, στο ίδιο προβολικό σύστημα με τις μετρήσεις των αισθητήρων (`survey_crs`). Γι' αυτό η υλοποίηση μπορεί να γίνει σε δύο βήματα:

| | Φάση 1 (ελάχιστη) | Φάση 2 (πλήρης, Β3) |
|---|---|---|
| Τι κάνει ο server | αποθηκεύει το αρχείο και τα μεταδεδομένα που δίνει ο χρήστης· φτιάχνει το zip του Β4 **χωρίς** μετατροπή κορυφών | μετατροπή σε ENU με PROJ, ένωση tiles, αυτόματη αναγνώριση CRS, προειδοποιήσεις |
| Εξαρτήσεις στον server | καμία νέα (μόνο `zipfile`) | `pymeshlab`, `pyproj`, workers |
| `frame` στο `model.json` | `"projected"` (Β4α) | `"enu"` (Β4) |
| Πότε δουλεύει | όταν το μοντέλο είναι σε μέτρα και στο **ίδιο** σύστημα με τα `survey` των αισθητήρων (Α2) | πάντα, σε οποιοδήποτε σύστημα, και σε πόδια ή μοίρες |

Στη φάση 1 ο server **πρέπει να απορρίπτει** (400, μήνυμα στον χρήστη) μοντέλο που δεν είναι σε μέτρα ή σε άλλο σύστημα από το `survey_crs` του έργου, αντί να το δέχεται: τα γυαλιά δεν μπορούν να το διορθώσουν και θα το έδειχναν σε λάθος θέση. Τα endpoints (Β2) και ο πίνακας (Β1) είναι ίδια και στις δύο φάσεις· η φάση 2 αλλάζει μόνο το τι μπαίνει στο πακέτο.

### Β2. Endpoints

Όλα με το υπάρχον JWT. Το έργο δίνεται **ρητά στο URL** και όχι μέσω του `current_project` του προφίλ: τα γυαλιά σήμερα αλλάζουν το `current_project` του χρήστη και αυτό επηρεάζει και την ανοιχτή web συνεδρία του.

| Μέθοδος | URL | Περιγραφή |
|---|---|---|
| `POST` | `/api/projects/{project_id}/models/` | multipart: `file`, `name`, `crs` (EPSG ή `"auto"`), `vertical`, `up_axis`, `units` → **202** `{id, status}` |
| `POST` | `/api/projects/{project_id}/models/detect-crs/` | multipart `file` (ή `id` υπάρχοντος) → `{suggestions: [{epsg, name, distance_m}]}` για το βήμα 2 της ροής |
| `GET` | `/api/projects/{project_id}/models/` | λίστα μοντέλων του έργου (όλα τα πεδία του Β1 εκτός από τα αρχεία) |
| `GET` | `/api/projects/{project_id}/models/{id}/` | ένα μοντέλο, μαζί με `status`, `progress`, `warnings` |
| `GET` | `/api/projects/{project_id}/models/{id}/package/` | το zip για τα γυαλιά: `ETag` = sha256, υποστήριξη `Range` (συνέχιση λήψης), `Content-Length` |
| `PATCH` | `/api/projects/{project_id}/models/{id}/` | αλλαγή `name` ή `crs` → νέα επεξεργασία |
| `DELETE` | `/api/projects/{project_id}/models/{id}/` | |

Δικαιώματα: όσοι βλέπουν το έργο βλέπουν και κατεβάζουν τα μοντέλα. Upload, αλλαγή και διαγραφή μόνο όσοι μπορούν να επεξεργαστούν το έργο.

**Απάντηση της λίστας** (αυτά τα πεδία διαβάζουν τα γυαλιά· μπορούν να υπάρχουν κι άλλα):

```jsonc
// GET /api/projects/12/models/
[
  {
    "id": "6f1c…",
    "name": "Κόνιτσα",
    "status": "ready",                // τα γυαλιά δείχνουν για λήψη μόνο τα "ready"
    "progress": 100,
    "error": null,
    "warnings": [],
    "source_crs": 2100,
    "units": 1.0,
    "package_sha256": "9b2e…",        // αλλάζει όταν αλλάζει το πακέτο → νέα λήψη
    "package_size": 84213555,         // bytes, για την μπάρα προόδου και τον έλεγχο χώρου
    "triangles": 480000,
    "textures": 4,
    "updated_at": "2026-10-26T10:12:00Z"
  }
]
```

**Κωδικοί που περιμένουν τα γυαλιά:**

| Κωδικός | Πότε | Τι κάνουν τα γυαλιά |
|---|---|---|
| `200` / `206` | πακέτο (`206` για `Range`) | λήψη / συνέχεια λήψης |
| `304` | `If-None-Match` ίδιο με το `ETag` | κρατούν το αποθηκευμένο |
| `401` | έληξε το access token | `POST /api/auth/refresh/` και ξανά |
| `403` / `404` | χωρίς δικαίωμα / διαγράφηκε | το σβήνουν από τη λίστα (το αποθηκευμένο μένει) |
| `409` | πακέτο ζητήθηκε ενώ `status` ≠ `ready` | «Σε επεξεργασία» |
| `413` | πακέτο πάνω από το όριο (Β5) | μήνυμα στον χρήστη |

### Β3. Επεξεργασία στο παρασκήνιο

Μετά το upload ή το `PATCH` του `crs`, ένα job (Celery / RQ / ό,τι χρησιμοποιεί ήδη το backend) καλεί **έτοιμη συνάρτηση Python που παραδίδουμε εμείς**:

```python
from quest_model_prep import prepare

result = prepare(
    source="/tmp/upload.zip",          # zip / obj / dxf / ifc
    crs=2100,                          # ή "auto"
    vertical="orthometric",
    up_axis="z", units=1.0,
    project_location=(40.0478, 20.7481),
    sensors=[(lat, lon, h), ...],      # survey θέσεις αισθητήρων, για έλεγχο και προειδοποιήσεις
    out_dir="/tmp/job-123/",
    progress=lambda pct: ...,
)
# result.package_path, result.sha256, result.origin (lat, lon, h),
# result.triangles, result.textures, result.warnings, result.detected_crs
```

Το backend αποθηκεύει μόνο το αποτέλεσμα στα πεδία του Β1. Η συνάρτηση:
- αποσυμπιέζει και ενώνει τα tiles σε ένα μοντέλο,
- μετατρέπει κάθε κορυφή από το `crs` σε τοπικό σύστημα **ENU** (μέτρα ανατολή / βορράς / πάνω) γύρω από την αρχή `origin` (WGS84), με PROJ (`Transformer(..., always_xy=True)`, ώστε συστήματα με σειρά αξόνων Β,Α όπως το EPSG:4326 να μη βγαίνουν καθρεφτισμένα). Η μετατροπή ανά κορυφή απορροφά και τον συντελεστή κλίμακας και τη σύγκλιση μεσημβρινών της προβολής, που αλλιώς θα φαίνονταν ως σφάλμα εκατοστών ανά 100 m στην ευθυγράμμιση,
- αν `crs="auto"`, δοκιμάζει τα πιθανά συστήματα για τη θέση του έργου (UTM ζώνης, εθνικό σύστημα, WGS84) και κρατά αυτό που πέφτει πάνω στους αισθητήρες,
- ελέγχει την απόσταση από τους αισθητήρες και γράφει προειδοποιήσεις (π.χ. διαφορά υψομέτρου ≈ υψόμετρο γεωειδούς → λάθος κατακόρυφο σύστημα),
- φτιάχνει το πακέτο (Β4).

**Απαιτήσεις server για το job:**
- Python ≥ 3.10 με `pymeshlab`, `pyproj` (μαζί με τα PROJ grids για γεωειδές, π.χ. `proj-data`), `pillow`.
- RAM: έως **16 GB** για μοντέλα πολλών εκατομμυρίων τριγώνων με υφές 16k.
- Προσωρινός δίσκος: περίπου **5×** το μέγεθος του upload.
- Χρόνος: λίγα λεπτά ανά μοντέλο. Τρέχει σε worker, όχι μέσα σε HTTP request.

### Β4. Μορφή πακέτου (zip)

Η εφαρμογή διαβάζει ήδη αυτή τη μορφή (φάκελος με ένα `.obj` + `model.json`). Προστίθενται μόνο τα πεδία `frame` και `origin*`.

```
konitsa.zip
├── model.obj          κορυφές σε μέτρα ENU γύρω από το origin, Z πάνω
├── model.mtl
├── tex_0.jpg …        υφές
└── model.json
```

```jsonc
// model.json
{
  "name": "Κόνιτσα",
  "format": "obj",
  "up": "z",
  "unitScale": 1,
  "georeferenced": true,
  "frame": "enu",                 // ΝΕΟ: κορυφές σε ENU γύρω από το origin
  "originLat": 40.0478123,        // ΝΕΟ
  "originLon": 20.7481456,        // ΝΕΟ
  "originH": 447.314,             // ΝΕΟ: στο ίδιο κατακόρυφο σύστημα με το "z" των αισθητήρων
  "projectId": 12,
  "sourceFile": "konitsa v.3.zip",
  "sourceCrs": 2100
}
```

### Β4α. Πακέτο φάσης 1 (`frame: "projected"`)

Ίδιο zip με το Β4, αλλά το `.obj` (ή `.dxf`) είναι το αρχείο του χρήστη όπως ήρθε, και το `model.json` δίνει το origin σε συντεταγμένες χάρτη αντί για WGS84. Η εφαρμογή διαβάζει ήδη όλα αυτά τα πεδία (τα ίδια που στέλνει σήμερα το `send_model.py` από το PC) εκτός από τα νέα `frame` και `crs`, που προσθέτουμε εμείς:

```jsonc
// model.json, φάση 1
{
  "name": "Κόνιτσα",
  "format": "obj",                // "obj" | "dxf"
  "up": "z",                      // "z" (τοπογραφικά/CAD) | "y" (Blender, SketchUp)
  "unitScale": 1,                 // μέτρα ανά μονάδα αρχείου· στη φάση 1 πάντα 1
  "georeferenced": true,
  "frame": "projected",
  "crs": 2100,                    // ΠΡΕΠΕΙ να είναι ίδιο με το survey_crs του έργου
  "originE": 222100.0,            // βλ. «Τι σημαίνει το origin» παρακάτω
  "originN": 4436500.0,
  "originH": 400.0,
  "projectId": 12,
  "sourceFile": "konitsa v.3.obj"
}
```

#### Τι σημαίνει το origin (ισχύει και για τις δύο μορφές)

Το origin είναι **η θέση στον χάρτη του σημείου (0,0,0) του αρχείου**. Οι κορυφές του αρχείου είναι **ήδη** σε σχέση με αυτό, και τα γυαλιά **δεν** το αφαιρούν από τις κορυφές· το χρησιμοποιούν μόνο για να τοποθετήσουν όλο το μοντέλο.

- Αρχείο με **απόλυτες** συντεταγμένες (κορυφές του τύπου 222135.5, 4436556.6): **χωρίς** `originE/N/H` (ή όλα 0). Τα γυαλιά διαλέγουν μόνα τους μια τοπική αρχή, για να μη χαθεί ακρίβεια στα float.
- Αρχείο με κορυφές **μετατοπισμένες** (κορυφές του τύπου 35.5, 56.6): `originE/N/H` = το ποσό που αφαιρέθηκε.
- **Ποτέ** και τα δύο: απόλυτες κορυφές **και** origin θα έστελναν το μοντέλο εκατοντάδες χιλιόμετρα μακριά. (Ακριβώς αυτό το σφάλμα διορθώθηκε στην εφαρμογή στις 26/10/2026, γιατί τα εργαλεία του PC και τα γυαλιά το ερμήνευαν διαφορετικά.)

Στη φάση 2 ισχύει το ίδιο με `originLat/Lon/H` και κορυφές ENU σε μέτρα γύρω από αυτό.

#### Τι θα ελέγχουν τα γυαλιά πριν εμφανίσουν το μοντέλο

(Υλοποιείται από εμάς μαζί με τη λήψη· γράφεται εδώ ώστε το backend να ξέρει τι απορρίπτεται.)

- `frame: "projected"`: το `crs` να είναι ίδιο με το `survey_crs` του έργου· αλλιώς δεν το τοποθετούν στο έργο και δείχνουν προειδοποίηση (μπορεί να εμφανιστεί μόνο ως μακέτα).
- Το μοντέλο να πέφτει κοντά στους αισθητήρες του έργου (μερικές εκατοντάδες μέτρα)· αλλιώς προειδοποίηση «το μοντέλο είναι μακριά από τους αισθητήρες».
- Κάθε τιμή αριθμός πεπερασμένος (όχι NaN / Infinity).
- `sha256` του zip ίδιο με το `package_sha256` / `ETag`· αλλιώς η λήψη απορρίπτεται και ξαναγίνεται.

### Β5. Αρχεία και όρια

- Upload: έως **5 GB** (`client_max_body_size` στο nginx). Καλό είναι να υποστηρίζεται συνέχιση (chunked / resumable upload, π.χ. tus), γιατί τα zip φωτογραμμετρίας είναι μεγάλα.
- Σερβίρισμα πακέτου από το nginx (`X-Accel-Redirect`) ή με presigned URL αν τα αρχεία είναι σε S3, όχι μέσα από το Django.
- Τα αρχικά uploads κρατιούνται, ώστε να μπορεί να γίνει νέα επεξεργασία (άλλο CRS, νέα έκδοση του `prepare`) χωρίς νέο upload.
- **Πακέτο για τα γυαλιά** (όρια που ελέγχει ήδη η εφαρμογή όταν αποσυμπιέζει): έως **300 MB** συμπιεσμένο, έως **500 αρχεία** μέσα στο zip, έως **1 GB** αποσυμπιεσμένο, ονόματα αρχείων χωρίς `..`, `/` στην αρχή, `\` ή `:` (ένας φάκελος, χωρίς υποφακέλους). Πάνω από περίπου 500 χιλιάδες τρίγωνα το Quest αρχίζει να κουράζεται· η φάση 2 κάνει decimation, στη φάση 1 καλό είναι μια προειδοποίηση στο upload.
- Λήψη μόνο μέσω **HTTPS** με έγκυρο πιστοποιητικό (το ίδιο με το υπόλοιπο API).

### Β6. Web UI (σελίδα έργου)

| Εφαρμογή Quest | ανάγνωση `frame` (`"projected"` / `"enu"`) + `crs` + `origin*`, λίστα «Μοντέλα έργου» από το Β2, λήψη με cache, συνέχιση και έλεγχο sha256, οι έλεγχοι του Β4α, χρήση του `survey` (Α2) για τη θέση των αισθητήρων |

## Ερωτήσεις προς την ομάδα του backend

1. Υπάρχει PostGIS στη βάση; (για το `ST_Transform` του Α2)
2. Ποιο σύστημα εργασιών παρασκηνίου χρησιμοποιείται (Celery, RQ, άλλο), και μπορεί να εγκατασταθεί `pymeshlab` / `pyproj` στους workers;
3. Πού αποθηκεύονται τα αρχεία (τοπικός δίσκος, S3);
4. Αποθηκεύεται κάπου το σύστημα συντεταγμένων των μετρήσεων ανά έργο, ή πρέπει να προστεθεί (Α1);
5. Υπάρχει ήδη μηχανισμός για μεγάλα uploads;
6. Ξεκινάμε με τη φάση 1 (Β0) ή κατευθείαν με τη φάση 2;
